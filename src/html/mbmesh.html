MB-System Unix Manual Page

mbmesh(1) General Commands Manual mbmesh(1)

NAME

mbmesh - reconstruct triangle meshes from swath bathymetry data

SYNOPSIS

mbmesh -I datalist [-O outputdir] [-R west/east/south/north] [-L meters] [--info] [output options] [-V] [-H]

DESCRIPTION

mbmesh reads swath sonar data through the MB-System datalist processing framework and reconstructs a triangle mesh from accepted bathymetry soundings. The program estimates local point spacing, derives default reconstruction settings, estimates oriented normals, reconstructs a signed scalar field with screened Poisson, extracts a surface with marching cubes, trims unsupported mesh regions, and writes the result as a binary glTF mesh.

The output mesh vertices are WGS84 Earth-Centered, Earth-Fixed (ECEF) coordinates in meters, following the conventions of mbgrd2gltf. Without --geoorigin the vertices are absolute ECEF coordinates. With --geoorigin they are offsets from the ECEF position of a GeoOrigin; the axes stay aligned with ECEF. An mbmesh product and an mbgrd2gltf product made with the same GeoOrigin therefore line up directly. GLB positions are 32-bit floats, so absolute ECEF coordinates resolve only about 0.5 m; use a GeoOrigin to preserve finer detail.

Reconstruction itself runs in a local east-north-up frame tangent to the WGS84 ellipsoid at the point below the centroid of the accepted soundings. Soundings are converted to ECEF and rigidly translated and rotated into this frame, so no map-projection distortion is introduced, and results are converted back to ECEF exactly on output. This frame does not depend on --geoorigin.

The default output is:

mesh.glb
Final triangle mesh in binary glTF format using the mbmesh local Cartesian coordinate frame.

Point cloud, diagnostic, and HTML viewer files are written only when requested with command-line output options.

OPTIONS

-I datalist, --input datalist
Input MB-System datalist file. This option is required unless the datalist path is supplied as the first non-option argument. If it names a directory instead, mbmesh reconstructs nothing and writes mbmesh_survey.html in the current directory: a viewer page with a check box for every .glb file beneath that directory, in accordions that mirror its layout, for example a survey directory with multibeam and lidar subdirectories. The chunk files and the tiles of a tileset are left out and its tileset.json is offered. The track.glb files are switched on when the page opens, the other GLBs are not. The page has an overview viewpoint over all the mbmesh GLBs found, as the page of a run does, with the GeoOrigin of the first. A GLB with another GeoOrigin, or with absolute vertices, does not line up with it, and is logged as an ERROR that names it. --geoviewpoint adds GeoViewpoints to its Viewpoint menu, without --html. With --cesium-html it also writes mbmesh_survey_cesium.html for CesiumJS. Run mbmesh in the survey directory or above it and serve that directory.
-O outputdir, --output outputdir
Output directory for generated files. The directory is created if needed. The default is mbmesh_output in the directory of the input datalist, so -I multibeam/datalistp.mb-1 writes multibeam/mbmesh_output.
-R west/east/south/north, --bounds west/east/south/north
Restrict accepted soundings to a geographic bounding box in degrees longitude and latitude.
-L meters, --lod meters, --level-of-detail meters
Requested smallest feature size in local meters. The Poisson cell is a quarter of it, but no finer than half the point spacing, so -L 0.2 gives a 5 cm cell even where the soundings are much denser. If omitted, mbmesh derives level of detail from the measured point spacing (twice the spacing), raised if needed to keep the reconstruction within about 500 million Poisson cells across the survey, and logs that it did so. A level of detail given here is never limited, but a warning is printed when it needs more than about 2 billion cells, which may take hours. The implementation clamps the resolved value to a supported range and uses it to derive default normal-estimation, Poisson, and trimming parameters. Use --info to see the resulting cell size and chunk plan before running.
--geoorigin[=lon,lat,elev], -G[lon,lat,elev]
Write vertices as ECEF offsets from a GeoOrigin, with the same syntax and meaning as in mbgrd2gltf. With a value, longitude and latitude in decimal degrees and elevation in meters above the WGS84 ellipsoid are all required. With no value, the GeoOrigin is the center of the data bounds at the mean sounding elevation. If the option is not given, vertices are absolute ECEF coordinates. GLB positions are 32-bit floats, so absolute ECEF (magnitudes of about 6.4 million meters) resolves only about 0.5 m; use a GeoOrigin to preserve sub-meter detail. As in mbgrd2gltf the value must be attached to the option: for the long form write an equals sign and no spaces, as in --geoorigin=-122.4,36.6,0; for the short form put the value directly after -G, as in -G-122.4,36.6,0. A value given as a separate argument, such as --geoorigin -122.4,36.6,0, is not accepted, and neither is a value with spaces unless it is quoted so that the shell passes it as one argument. With --html, the viewer page positions the model with GeoOrigin and GeoViewpoint nodes.
--geoviewpoint=VALUES
With --html, add a GeoViewpoint to the page; the option can be repeated, and each adds a GeoViewpoint, written with its position as latitude, longitude and elevation and the GeoOrigin used again, named USER_GEOVIEW_1, USER_GEOVIEW_2 and so on, to the Viewpoint menu of the page, after the two overview viewpoints, where Page Down also steps through them. The values are geodetic, in the order of --geoorigin, longitude first, so they do not depend on the GeoOrigin or the data and can be used again in another run: lon,lat,elev,clon,clat,celev, the camera position and the point it looks at, or lon,lat,elev,ax,ay,az,angle,clon,clat,celev, with the orientation as an axis and an angle, as a GeoViewpoint takes it. Heights are above the ellipsoid. Without an orientation the top of the view is toward local up. The Copy GeoViewpoint button of the page gives the ten-number form for the view on the screen, on the clipboard and in the X3DOM log. The value must be attached to the option, with an equals sign and no spaces, for example --geoviewpoint=-122.4,36.6,-900,-122.39,36.61,-950.
--pointcloud-colormap=NAME
How pointcloud.glb is colored by height, with the Haxby color table that mbm_grdplot uses, 11 colors from dark blue to white: linear (the default), 11 equal steps between rounded heights chosen from the range, as mbm_grdplot -G5 does; equalized, steps with equal numbers of points, as mbm_grdplot -G5 -S does; or none, one orange. The heights the color changes between are in the description of the file's MB-System.content metadata.
--no-colors
With --tileset, do not color the tiles by height. By default every vertex has a color (COLOR_0) from the Haxby table over the heights of the whole survey, so that all tiles agree, with a white base color; tileset.json records the bounds as heightColors, and the page of --html has a "color by height" checkbox that turns the colors off, which shows the tiles in gray.
--lift[=METERS]
With --tileset, lift the tileset above the ellipsoid along the local vertical, in the transform of tileset.json. As --geoorigin works, without the option the tileset has the true heights (a warning says so if any are below the ellipsoid), the option alone takes the default, and a value must be attached, as in --lift=900. X3DOM's GeoTileset takes the height of the camera as at least 1 m, so tiles below the ellipsoid, as seafloor is, never get near enough to refine. The default lift puts the lowest point of the mesh 10 m above the ellipsoid, to a meter, if it is lower. The lift is logged and written as liftMeters in the extras of tileset.json. The page of --html puts its other models in GeoTransform nodes that lift them the same, raises the viewpoints, and sets the maximumScreenSpaceError of the GeoTileset to 1 pixel. The Copy GeoViewpoint button takes the lift off again, so the option it gives is for the true heights.
--chunk-size meters
Reconstruct in square horizontal chunks of about this size (rounded up to a whole number of Poisson cells) instead of in one pass. Chunking turns on automatically when a single Poisson grid would exceed about 8 million cells. See Chunked reconstruction below.
--chunk-halo meters
Read this many meters of neighboring points beyond the edge of each chunk, rounded up to a whole number of Poisson cells. The default is the reach of the normal estimation, splatting and trimming. A halo smaller than that reach is used, with a warning. A larger halo needs more memory, disk and time, because every chunk reconstructs its halo again, and it changes the chunk size; it did not improve the match of neighboring chunks at their edges. It has an effect only when the run is chunked.
--no-draco
Write the triangle meshes of the GLB files as arrays of 32-bit floats and integers. By default mesh.glb, raw_mesh.glb, the chunks and the tileset tiles are compressed with Draco (the glTF extension KHR_draco_mesh_compression), which makes them about a tenth of the size. The point cloud, normals, sensor positions and track are never compressed, since the extension is for triangles.
--draco-precision meters
With Draco, keep the positions to this many meters (default 0.001). Each file gets the number of bits (8 to 30) that makes the step of its quantization no more than this over its extent.
--draco-normal-bits n
With Draco, the bits of each normal, 2 to 30 (default 10).
--seam-method name
How chunks are matched on the edges they share: solve (the default) solves each chunk with the final fields of its west and south neighbors held fixed on the shared edges, which removes the edge effect on those sides, but a chunk waits for those neighbors before its solve, so fewer chunks are solved at the same time, and the threads without a chunk to solve share the sweeps of the solver of those that have one. The output does not depend on the number of threads. blend solves each chunk free, all of them at the same time, and then blends its field to the neighbors' over --seam-blend.
--seam-blend meters
With --seam-method blend, over this width on each side of an edge between two chunks, the Poisson field of a chunk is made to match the final field of the chunk to its west or to its south on that edge, so that the two meshes meet exactly, with no step and no gap. The fields of neighboring chunks are solved apart and differ where they meet (by about 2 cm on one multibeam survey at -L 0.1). The chunks share one lattice of grid nodes, so with the same field values on the nodes of an edge, marching cubes makes the same vertices along it; the correction is the difference on the edge, fading smoothly to zero over the width. The vertices that the chunks have in common are merged in mesh.glb. The default is 1 m, or a quarter of the chunk size if that is less. Zero does not match the chunks, and lets them be started in any order; with a width the chunks are started in order, since a chunk waits for its neighbors. It has an effect only when the run is chunked.
--label-chunks
With --html, the page draws the outline of each chunk, at the mean height of its surface, and its file name, for example chunk_2_-10.glb, as text that faces the viewer, one text height above the highest point of the chunk. A check box switches them off. It is for finding which chunk a seam, a void or an overhang belongs to. It needs a chunked run. The survey page that a directory input writes draws them too, for the chunk files in the chunks directories beneath it that say where their chunk is (each carries it in MB-System.content.chunkLabel); those of a run made before that was written are not drawn.
--chunk i,j
Reconstruct only chunk (i,j). Chunk (i,j) covers x from i*size to (i+1)*size and y from j*size to (j+1)*size in the local east-north frame. Intended for testing. Each of i and j can be a range first..last, both included, so that --chunk 2..3,-11..-10 is four chunks, and the option can be repeated, to add chunks: --chunk 2,-10 --chunk 3,-10 is two neighbors, for looking at the seam between them. mesh.glb and the pages then hold only those chunks.
--max-chunks n
Stop after n chunks. Intended for testing.
--threads n
Number of chunks reconstructed at the same time when chunking. The default is the smaller of the number of processor cores and 4. Each chunk holds its own Poisson grid, so memory use grows with this value. With automatic chunking, a larger value also gives smaller chunks, since at least two chunks per thread are wanted. The output does not depend on it.
--void-size m
Put back voids of up to m meters across (default 2) that support trimming would remove from inside the surface. The sonar returns thin out in the depressions of the seafloor and under overhangs, so the surface bridging such a gap has too few soundings near it and is trimmed, leaving a hole in a surface that is otherwise there. A raster of the soundings of the whole survey, with their heights, shows where they are. A mesh vertex that was rejected only for too few neighbors is kept if it has a sounding within three support radii, or if its nearest sounding is within half this size, soundings are all around it in the tangent plane of the mesh, and the nearest soundings are beside it and not above it. Pieces of the surface that are not joined to the rest and are smaller than a quarter of the area of a disk of this size are taken out. Gaps at the edge of the survey stay trimmed, as does surface that disagrees with the soundings, except for holes that are entirely surrounded by surface that is kept, which are filled up to the area of a disk of this size. Zero trims all of them.
--island-size m
When the survey is reconstructed in chunks, remove from mesh.glb the pieces of the merged mesh that are not joined to the rest and have an area of up to that of a disk m meters across (default 2), if fewer than half of their vertices have a sounding within a support radius, in three dimensions, as the raster of the soundings knows them. Small pieces with soundings under them, such as rock that the trimming cut from the rest, stay. Zero keeps all of them. raw_mesh.glb is not cleaned.
--primitive-size m
Write mesh.glb and raw_mesh.glb as one mesh of many primitives, one for each square of this many meters of the local east-north frame (anchored at its origin), as mbgrd2gltf writes blocks of 256 cells. Each primitive has the vertices that its triangles use and, with Draco, its own compressed stream, so a viewer decodes and draws the surface in parts and not as one array of tens of millions of vertices. The default is 256 Poisson cells. Zero writes one primitive. The vertices on the edges of the squares are in both primitives. The chunk files and the tiles of a tileset are one primitive each.
--spill-points n
A survey with more than n accepted soundings (default 50000000) is not held in memory. The soundings are written to a file in a directory mbmesh_work beside the results, and then sorted into one file per chunk, each holding the points of the chunk and of its halo, so that memory use follows the size of a chunk and not of the survey. Each chunk is reconstructed from its file and gives the same mesh as from memory. The directory is deleted when the run ends. The disk needs 28 bytes for each sounding for the spill file, and 48 bytes for each point, about 1.3 times as many as there are, for the chunk files, which are small when --decimate is on. Use -O to put the work directory on a disk with room. 0 always spills. Chunking, which this needs, is turned on for such a survey. The files that hold points as one file, pointcloud.glb, origins.glb, normals.glb and the oriented PLY, then hold one point in n, so that there are at most 5 million; the xyz files hold every point. The log gives the peak memory of the process after each stage.
--poisson-solver name
Select how the Poisson grid equation is solved: sor, the default, which is red-black successive over-relaxation, updated in place, or jacobi. An iteration of either costs about the same, but sor converges in far fewer, so it needs a much smaller number of iterations, which it chooses itself; on a test survey about 100 of its iterations reached the residual of 473 Jacobi iterations.
--poisson-iterations n
Number of iterations of the solver, from 1 to 100000, for either solver. By default sor takes one iteration per cell across the longest edge of each chunk's grid, but at least 50, and jacobi takes a count chosen from the level of detail, between 200 and 500. The relative residual after the iterations, which shows how far the solver converged, is logged with -V for each chunk and at INFO level in a single pass.
--decimate meters
Enable voxel-grid point decimation with the specified cell size in local meters. The legacy single-dash form -decimate is also accepted.
--info
Print dataset information and the reconstruction plan, and exit before mesh reconstruction. This includes input counts, geodetic bounds, the estimated point spacing, and the resulting Poisson cell size, chunk plan and cell count. This option was called --metadata in earlier versions; --metadata is no longer accepted.
-V, --verbose
Enable progress and diagnostic logging. Messages use the same line format as mbgrd2gltf: level, local date and time, source file, function and line, then the message, for example INFO 2026-10-19 14:35:15.419 mbmesh.cpp main():151 [startup] .... Without -V, INFO, WARN and ERROR lines are shown. When chunking, these include at most one progress line a minute (chunks finished, percentage, elapsed time and an estimate of the time left) and a final line with the time spent in each stage, added up over all chunks; in a single pass they include one line for each finished stage. -V adds DEBUG lines with the start of each stage and a line for each chunk. All messages go to standard error.
-H, -h, --help
Display help message and exit.

OUTPUT OPTIONS

Every long option in this section also accepts a legacy single-dash form (e.g. -html, -diagnostics, -all-outputs) for backward compatibility.

--html
Also write an X3DOM viewer page, in the parent of the output directory and named after it (for example mbmesh_output.html beside mbmesh_output), and print the command to serve and view it. The page is laid out like the one mbgrd2gltf writes: a heads-up display with the navigation mode, the debug displays and the view controls, a check box for each GLB, and a panel with the processing log of the run (see OUTPUT FILES). mbmesh does not start a web server or a browser; run the printed command (python3 -m http.server 8000 --bind 127.0.0.1 --directory webroot, where the web root is the parent of the output directory) in a terminal, press Ctrl-C to stop it, and open the printed URL.
--xyz
Also write both local and ECEF XYZ point cloud files.
--local-xyz
Also write pointcloud-local.xyz, containing accepted and decimated soundings in the local Cartesian coordinate frame used for reconstruction. This is the same coordinate frame used by mesh.glb.
--ecef-xyz
Also write pointcloud-ecef.xyz, containing accepted and decimated soundings in WGS84 Earth-Centered, Earth-Fixed coordinates.
--oriented-ply
Also write oriented-pointcloud-ecef.ply, an oriented point cloud suitable for inspection.
--pointcloud-glb
Also write pointcloud.glb, a diagnostic GLB point cloud for smaller datasets. The points are colored by their height in the local frame, in a COLOR_0 attribute, the way mbm_grdplot -G5 -S colors a grid: the Haxby color table, 11 colors from dark blue to white, changing linearly between heights that divide the points into 11 cells of equal numbers. Those heights are in the description of the file's MB-System.content metadata.
--normal-glb
Also write normals.glb, diagnostic normal vectors for smaller datasets.
--origin-glb
Also write origins.glb, diagnostic sensor-origin rays for smaller datasets.
--track-glb
Also write track.glb, the sensor track as a black 3D line, with one position per ping. The positions are in the same coordinates as mesh.glb, including any --geoorigin offset, so the two overlay directly.
--tileset
Also write the surface as an OGC 3D Tiles 1.1 tileset, tileset/tileset.json and one tileset/L0/tile_I_J.glb for each reconstruction chunk (one tile, tile_0_0.glb, if reconstruction is not chunked), so that a viewer can load a part of a survey at a time; a browser will not load a GLB of more than 2 GiB. The vertices of a tile are in the local east-north-up frame of the reconstruction, written Y-up as glTF requires (X east, Y up, Z south), and the transform of the root tile places that frame on the Earth in WGS 84 ECEF, so the tileset does not depend on --geoorigin. The root has no content and its children are the tiles, each with a box bounding volume and a geometric error of 0; the geometric error of the root is the diagonal of its box. The georeference, provenance and MB-System blocks are written in the extras of the tiles and of tileset.json, with vertexCoordinates localFrame. With --html the page shows the tileset with a GeoTileset node in place of mesh.glb; X3DOM has that node only in its master of October 2026, so use --x3dom-url.
--cesium-html
Also write a viewer page for CesiumJS, with a check box for each GLB and tileset, beside the output directory (mbmesh_output_cesium.html) and inside it (mbmesh_cesium.html). The globe of Cesium would hide data below the ellipsoid, so the page starts with it hidden and has a check box that shows it, translucent. Tilesets are shown at their true height whatever --lift says. The page has the Viewpoint menu, the --geoviewpoint viewpoints, a Copy viewpoint button and the scale axes, but no chunk outlines or labels. It must be served over HTTP, like the --html page. With a directory input it also writes mbmesh_survey_cesium.html.
--cesium-url url
The directory of the CesiumJS build that the --cesium-html page loads, with Cesium.js and Widgets/widgets.css in it (default https://cesium.com/downloads/cesiumjs/releases/1.114/Build/Cesium).
--x3dom-url url
The X3DOM script that the page written by --html loads, and the stylesheet x3dom.css beside it. The default is the build on www.x3dom.org, which has no GeoTileset node.
--raw-mesh-glb
Also write raw_mesh.glb, the untrimmed triangle mesh produced by marching cubes before support trimming.
--diagnostics
Also write pointcloud.glb, normals.glb, and origins.glb.
--all-outputs
Write all optional output files.

EXAMPLES

Reconstruct a mesh and write the default mesh.glb:

mbmesh -Idatalist.mb-1

Write the mesh, X3DOM viewer, and local/ECEF XYZ point clouds:

mbmesh -Idatalist.mb-1 -O output/mbmesh_run --html --xyz -V

Restrict processing to a geographic region and request a coarser level of detail:

mbmesh -Idatalist.mb-1 -R-122.5/-121.8/36.5/37.2 -L 0.5 -V

Print dataset information and the reconstruction plan without reconstructing a mesh:

mbmesh -Idatalist.mb-1 --info

OUTPUT FILES

mbmesh always writes mesh.glb. Optional files are written only when their corresponding output options are supplied.

mesh.glb
Final trimmed triangle mesh in binary glTF format. Vertex positions are ECEF coordinates, or ECEF offsets from the GeoOrigin when --geoorigin is used. When reconstruction is chunked this is the merged mesh of all chunks.
Every GLB records where it is and how it was made in its glTF asset.extras, in three blocks. georeference gives the coordinate reference system (EPSG:4978), whether the vertices are absolute or relativeToCenter, the center (the GeoOrigin as ECEF meters, with absolute = vertex + center), the same point as geodeticCenter (longitude, latitude, height), the heightReference (the ellipsoid) and the extent of the data. provenance gives the software and version, the time of execution (UTC), the command line, working directory, user and host, and the input datalist, formats and swath files. MB-System gives what the file holds (mesh, chunk, track, and so on), the sounding counts, the reconstruction settings and the vertical reference. The page written by --html holds the same in X3D GeoMetadata and WorldInfo nodes. See src/mbmesh/GEOREFERENCE.md for the names. The vertical reference has no geoid correction: a sounding's depth, negated, is used as a height above the WGS 84 ellipsoid.
chunks/chunk_I_J.glb
Written only when reconstruction is chunked: one file per chunk, with vertices placed exactly as in mesh.glb.
tileset/tileset.json, tileset/L0/tile_I_J.glb
Optional OGC 3D Tiles tileset of the surface; see --tileset. mbglb2tiles writes the same layout into the same directory by default, with coarser levels as well, and replaces this tileset.
raw_mesh.glb
Optional untrimmed triangle mesh before support trimming.
<outputdir>/mbmesh.html
The same page inside the output directory: it refers to its models by their names there and offers none from beside the directory, so it works when the web server is rooted higher up, for example at a survey directory. Written with --html.
<outputdir>.html
Optional X3DOM viewer page, written in the parent of the output directory and named after it, for example mbmesh_output.html. The parent is the root of the web server, so the page refers to its models by paths relative to it, such as mbmesh_output/mesh.glb. It is titled with the last three directories of the web root, which identify the survey, for example OceanImaging2018/20180923d1/multibeam. It is laid out in the style of the page mbgrd2gltf writes, with a heads-up display and a Processing Log panel, opened with the button at the bottom left, which shows every message of the run up to DEBUG level, whether or not -V was used: the command line, the settings, the timing of each stage and, when chunking, of each chunk. At most 20,000 messages are kept, and the log says how many were left out. The log is written to mbmesh.log in the output directory, one message a line, and not into the page, which it would make large and hard to edit; the page loads it when the panel is first opened, so it must be served over HTTP. The log is written last so that it is complete.
The page has a check box for every GLB it can show: the .glb files in the output directory, with mesh.glb and track.glb first, and then the .glb files in the web root beside the output directory, such as the product of mbgrd2gltf. mesh.glb and track.glb are shown when the page opens; the others are loaded when first switched on. The chunk files are not listed. GLBs from the web root line up with the mesh only if they use the same GeoOrigin. Browsers will not load GLB files from a file URL, so the page must be served.
pointcloud-local.xyz
Optional XYZ point cloud in the same local Cartesian coordinate frame as mesh.glb.
pointcloud-ecef.xyz
Optional WGS84 Earth-Centered, Earth-Fixed XYZ point cloud.
oriented-pointcloud-ecef.ply
Optional oriented ECEF point cloud.
pointcloud.glb
Optional diagnostic point cloud GLB, colored by height.
normals.glb
Optional diagnostic normal-vector GLB.
origins.glb
Optional diagnostic sensor-origin-ray GLB.
track.glb
Optional sensor track, drawn as line segments through the sensor position of each ping that contributes an accepted sounding. The track is broken where the swath file changes, where the time runs backwards, and where the time between two pings is more than ten times the median ping interval of the file, so that it does not run straight across the turns between survey lines or across gaps in the data.

PROCESSING NOTES

Sounding filtering
mbmesh uses MB-System datalist processing and accepts valid bathymetry soundings. Geographic filtering is applied when -R is specified.

Coordinate frame
mbmesh converts each sounding and sensor position to WGS84 ECEF coordinates and then to a local east-north-up frame (see above). Sounding elevation is taken as negative bathymetry, and sensor elevation as negative sensor depth, both treated as heights above the WGS84 ellipsoid. The optional ECEF point-cloud outputs apply the exact inverse transform.

Chunked reconstruction
A single screened-Poisson grid covers the bounding box of its input, so memory and run time grow quickly with survey size and level of detail. In chunked mode the survey is divided into square horizontal chunks on a fixed lattice anchored at the local-frame origin. Each chunk is reconstructed from its own points plus a surrounding halo of neighboring points, on a Poisson grid aligned to a lattice shared by all chunks, and keeps only the triangles whose centroids fall inside it. Chunks are reconstructed in parallel and delivered in chunk order. All soundings are still read into memory before chunking, and chunk edges are not welded, so small steps or cracks can occur where chunks meet.

Automatic settings
The program estimates point spacing from nearest-neighbor distances inside blocks of consecutive soundings, which does not depend on the number of soundings, and derives default normal-estimation, screened-Poisson, marching-cubes, and support trimming settings from the data and requested level of detail.

Support trimming
Unsupported mesh regions are removed after marching cubes, except for the voids inside the surveyed surface that --void-size puts back. If trimming removes the entire mesh, mbmesh exits with an error rather than writing an empty surface.

MB-SYSTEM INTEGRATION

mbmesh integrates with the MB-System datalist processing framework and can read swath files in MB-System supported formats.
